# 02.4 — Altura e Sistema de Notas

## 1. Objetivo

Definir como o Music Engine representa a altura musical de uma nota de forma precisa, independente da forma como ela é desenhada na pauta.

A representação interna deve permitir que a mesma informação seja usada por edição, renderização, reprodução, transposição, importação/exportação e futura escrita manuscrita.

Princípio:

> **A nota é um objeto musical; sua aparência na pauta é uma representação desse objeto.**

---

## 2. Conceitos fundamentais

Uma nota possui pelo menos duas dimensões independentes:

- **altura (pitch)** — qual som/notação representa;
- **posição temporal** — quando começa;
- **duração** — quanto tempo permanece.

Neste documento o foco é a altura.

A altura deve ser tratada como dado estruturado, e não como uma string livre.

Exemplo conceitual:

```json
{
  "step": "C",
  "alter": 0,
  "octave": 4
}
```

---

## 3. Sistema diatônico básico

O sistema inicial reconhece os sete nomes fundamentais:

| Step | Nome internacional | Nome em português |
|---|---|---|
| C | Dó | Dó |
| D | Ré | Ré |
| E | Mi | Mi |
| F | Fá | Fá |
| G | Sol | Sol |
| A | Lá | Lá |
| B | Si | Si |

O campo `step` deve usar sempre a convenção internacional `A`–`G`.

A interface poderá exibir nomes em português quando apropriado.

---

## 4. Oitava

A nota precisa incluir uma oitava explícita.

Exemplo:

```text
C3
C4
C5
```

representam a mesma classe de nota em registros diferentes.

O sistema não deve armazenar apenas `C`, pois isso perderia informação necessária para posicionamento, reprodução e transposição.

Estrutura mínima:

```json
{
  "step": "C",
  "alter": 0,
  "octave": 4
}
```

---

## 5. Alteração cromática

A alteração da altura deve ser separada do nome fundamental.

Campo:

```text
alter
```

Representação inicial:

| Valor | Significado |
|---:|---|
| -2 | dobrado bemol |
| -1 | bemol |
| 0 | natural |
| +1 | sustenido |
| +2 | dobrado sustenido |

Exemplos:

```json
{ "step": "F", "alter": 0, "octave": 4 }
```

```json
{ "step": "F", "alter": 1, "octave": 4 }
```

```json
{ "step": "B", "alter": -1, "octave": 4 }
```

A alteração pertence à representação da nota e não deve ser codificada dentro de uma string como `F#4`.

---

## 6. Altura escrita × altura sonora

O sistema precisa distinguir:

1. **identidade notacional** — como a nota é escrita;
2. **altura sonora efetiva** — frequência/classe cromática resultante.

Isso é fundamental para enarmonia.

Por exemplo, `C#4` e `Db4` podem produzir a mesma altura sonora em um sistema temperado, mas possuem identidades notacionais diferentes.

Portanto:

> **Enarmonia não deve apagar a grafia musical original.**

---

## 7. Valor cromático interno

Para cálculos, o Music Engine deve conseguir converter uma nota para uma posição cromática absoluta.

Uma convenção inicial pode usar semitons MIDI-like, sem obrigar a interface a expor MIDI.

Referência conceitual:

```text
C = 0
C#/Db = 1
D = 2
D#/Eb = 3
E = 4
F = 5
F#/Gb = 6
G = 7
G#/Ab = 8
A = 9
A#/Bb = 10
B = 11
```

Com a oitava, obtém-se uma posição cromática absoluta.

Essa camada é útil para:

- comparação de alturas;
- transposição;
- reprodução;
- intervalos;
- validações;
- MIDI futuro.

Ela não substitui `step + alter + octave`.

---

## 8. Regra de dupla representação

A nota deve manter a representação notacional e permitir cálculo cromático.

Conceitualmente:

```text
Pitch
├── step
├── alter
├── octave
└── valor cromático derivado
```

O valor cromático deve ser derivado ou calculado de maneira determinística, evitando duas fontes independentes de verdade.

---

## 9. Enarmonia

O Music Engine deve preservar a grafia solicitada pelo usuário.

Exemplo:

```text
C#4 ≠ Db4
```

como objetos notacionais, mesmo que possam representar a mesma altura sonora.

Isso será importante para:

- armaduras;
- escalas;
- transposição inteligente;
- análise harmônica futura;
- leitura correta da partitura;
- importação MusicXML;
- escrita manuscrita.

Uma futura operação explícita poderá converter enarmonias, mas isso deverá ser uma transformação consciente, não uma normalização automática.

---

## 10. Faixa de altura

O modelo não deve limitar artificialmente a altura às notas normalmente exibidas por uma pauta.

O domínio deve aceitar uma faixa suficientemente ampla para representar instrumentos e usos distintos.

Limitações específicas de instrumento serão responsabilidade futura de uma camada de **Instrument Model**, e não do objeto básico `Pitch`.

---

## 11. Posição na pauta não é parte do Pitch

A posição gráfica da nota depende da clave.

Por exemplo, a mesma nota `C4` pode aparecer em posições gráficas diferentes dependendo da clave utilizada.

Portanto:

```text
Pitch → informação musical
Clef → regra de interpretação gráfica
Renderer → desenho
```

O Music Engine nunca deve armazenar algo como “quinta linha da pauta” como substituto da altura.

---

## 12. Interação com o editor

Quando o usuário clicar/tocar em uma posição da pauta, a interface poderá inicialmente interpretar a posição gráfica e convertê-la para um `Pitch`.

Fluxo:

```text
Clique/toque
    ↓
Posição gráfica
    ↓
Clave atual
    ↓
Pitch
    ↓
Music Engine
    ↓
Evento Musical
```

O caminho inverso também precisa existir:

```text
Pitch
    ↓
Clave atual
    ↓
Posição gráfica
    ↓
Renderer
```

Assim, entrada e saída permanecem coerentes.

---

## 13. Nota natural

Uma nota natural deve ser representada explicitamente como `alter: 0`.

Exemplo:

```json
{
  "step": "E",
  "alter": 0,
  "octave": 4
}
```

Não devemos usar `null`, ausência do campo ou diferentes convenções para significar natural.

Isso simplifica validação e transformação.

---

## 14. Acidente escrito × alteração efetiva

Este documento define a altura estrutural da nota. A forma como um acidente é exibido na partitura será tratada no documento **02.6 — Acidentes**.

Isso permite distinguir futuramente:

```text
altura estrutural da nota
        ↓
regras da armadura
        ↓
regras de acidentes locais
        ↓
acidente efetivamente exibido
```

A existência de um `alter` no objeto de nota não deve, sozinha, definir todas as regras de notação visual.

---

## 15. Transposição

A transposição deve operar sobre objetos musicais estruturados.

Uma operação futura poderá ser conceitualmente:

```text
transpose(pitch, interval)
```

A operação deve poder preservar ou escolher uma grafia enarmônica adequada, conforme o contexto musical.

Isso reforça a necessidade de não armazenar altura apenas como texto.

---

## 16. Compatibilidade futura

O modelo deve ser capaz de receber informações provenientes de:

- mouse;
- touch;
- teclado;
- MIDI;
- MusicXML;
- escrita manuscrita reconhecida;
- importação de outros formatos.

Todos devem convergir para o mesmo objeto de altura.

```text
Mouse ───────┐
Touch ───────┤
Teclado ─────┤
MIDI ────────┤ → Pitch → Music Engine
MusicXML ────┤
Manuscrito ──┘
```

---

## 17. Exemplo completo

Uma nota musical poderá futuramente assumir uma estrutura semelhante a:

```json
{
  "type": "note",
  "pitch": {
    "step": "F",
    "alter": 1,
    "octave": 4
  },
  "duration": {
    "base": "quarter",
    "dots": 0,
    "tuplet": null
  },
  "position": 480
}
```

Nesse exemplo:

- `F` identifica o nome fundamental;
- `1` representa sustenido;
- `4` identifica a oitava;
- a duração é uma semínima;
- a posição temporal é 480 ticks.

Cada dimensão possui responsabilidade própria.

---

## 18. Regras para o Music Engine

O Music Engine deve:

1. validar `step` contra `A–G`;
2. validar a oitava segundo a faixa suportada pelo sistema;
3. validar `alter` segundo os valores permitidos;
4. preservar a grafia enarmônica;
5. permitir cálculo cromático derivado;
6. nunca usar posição gráfica como fonte de verdade para a altura;
7. receber e devolver objetos estruturados;
8. manter altura independente de duração e posição temporal.

---

## 19. Critérios de aceitação

O domínio será considerado adequado quando:

- `C4` puder ser representado sem ambiguidade;
- `F#4` e `Gb4` puderem coexistir como grafias distintas;
- notas naturais tiverem representação consistente;
- a oitava fizer parte da identidade da nota;
- o sistema puder comparar alturas cromaticamente;
- a renderização puder mudar de clave sem alterar o `Pitch`;
- transposição puder operar sobre dados estruturados;
- futuras entradas MIDI e manuscrito puderem produzir o mesmo modelo.

---

## 20. Decisões deste documento

| ID | Decisão |
|---|---|
| MUSIC-013 | Altura será representada por `step + alter + octave`. |
| MUSIC-014 | A convenção interna dos nomes fundamentais será `A–G`. |
| MUSIC-015 | Alterações cromáticas serão representadas numericamente. |
| MUSIC-016 | Enarmonia será preservada como identidade notacional. |
| MUSIC-017 | Valor cromático será derivado, não uma segunda fonte de verdade. |
| MUSIC-018 | Pitch será independente da clave e da posição gráfica. |
| MUSIC-019 | Nota natural será representada explicitamente por `alter: 0`. |
| MUSIC-020 | Regras de acidentes visuais serão tratadas separadamente do Pitch. |
