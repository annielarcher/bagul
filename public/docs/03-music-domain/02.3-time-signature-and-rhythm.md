# 02.3 — Fórmula de Compasso e Estrutura Rítmica

**Status:** Aprovado para a arquitetura do domínio  
**Área:** 03 — Domínio Musical  
**Documento:** 02.3  

## 1. Objetivo

Definir como o sistema representa, interpreta e valida a fórmula de compasso e a estrutura rítmica de cada compasso da partitura.

Este documento estabelece uma distinção fundamental do projeto:

> **Capacidade temporal de um compasso não é a mesma coisa que agrupamento rítmico.**

O Music Engine deve saber quanto tempo cabe em um compasso, mas também deve preservar a forma musical como esse tempo é organizado e apresentado.

---

## 2. Conceitos fundamentais

Uma fórmula de compasso será tratada como uma estrutura musical, e não apenas como o texto visual `4/4`.

Ela deve responder pelo menos às seguintes perguntas:

- quanto tempo cabe no compasso?
- qual unidade é indicada pelo denominador?
- qual é a unidade de pulso predominante?
- como os tempos são agrupados?
- como o ritmo deve ser visualmente organizado?

Modelo conceitual:

```text
TimeSignature
├── numerator
├── denominator
├── capacity
├── beatUnit
├── beatPattern
└── grouping
```

---

## 3. Numerador e denominador

### 3.1 Numerador

Indica a quantidade de unidades representadas pela fórmula.

Exemplo:

`4/4` → quatro unidades de semínima.

### 3.2 Denominador

Indica qual figura musical representa uma unidade de referência.

Mapeamento inicial:

| Denominador | Figura |
|---:|---|
| 1 | semibreve |
| 2 | mínima |
| 4 | semínima |
| 8 | colcheia |
| 16 | semicolcheia |
| 32 | fusa |

O denominador não deve ser confundido automaticamente com o pulso percebido. Isso é especialmente importante em compassos compostos e assimétricos.

---

## 4. Capacidade temporal

A capacidade representa a quantidade total de tempo que pode ocupar um compasso antes que ele seja considerado completo.

Usando a resolução interna definida em `02.2`:

```text
semínima = 480 ticks
```

A capacidade pode ser calculada conceitualmente por:

```text
capacity = numerator × value(denominator)
```

Exemplos:

| Fórmula | Capacidade |
|---|---:|
| 2/4 | 960 ticks |
| 3/4 | 1440 ticks |
| 4/4 | 1920 ticks |
| 5/4 | 2400 ticks |
| 4/2 | 3840 ticks |
| 6/8 | 1440 ticks |
| 9/8 | 2160 ticks |
| 12/8 | 2880 ticks |

Essa matemática define **quanto cabe**, não necessariamente **como deve ser agrupado**.

---

## 5. Unidade de compasso x unidade de pulso

O projeto deve separar três ideias:

```text
unidade indicada pela fórmula
        ↓
unidade de referência
        ↓
pulso musical percebido
```

Em `4/4`, por exemplo, a semínima é a unidade indicada e normalmente também funciona como pulso.

Em `6/8`, seis colcheias cabem no compasso, mas a organização musical mais comum é em dois pulsos principais de três colcheias:

```text
6/8
[ ♪ ♪ ♪ ] [ ♪ ♪ ♪ ]
   pulso      pulso
```

Portanto, o Music Engine não deve inferir toda a estrutura musical apenas do denominador.

---

## 6. Agrupamento rítmico

O agrupamento descreve como o conteúdo temporal é organizado em unidades perceptivas e gráficas.

Exemplos:

### 6/8

```text
3 + 3
```

### 9/8

```text
3 + 3 + 3
```

### 12/8

```text
3 + 3 + 3 + 3
```

### 5/8

Pode ser:

```text
2 + 3
```

ou:

```text
3 + 2
```

### 7/8

Pode ser:

```text
2 + 2 + 3
2 + 3 + 2
3 + 2 + 2
```

Essas possibilidades não são equivalentes do ponto de vista musical, mesmo quando possuem a mesma capacidade temporal.

---

## 7. Modelo de dados inicial

Representação conceitual:

```json
{
  "numerator": 4,
  "denominator": 4,
  "beatUnit": "quarter",
  "grouping": [4]
}
```

Exemplo de `6/8`:

```json
{
  "numerator": 6,
  "denominator": 8,
  "beatUnit": "dotted-quarter",
  "grouping": [3, 3]
}
```

Exemplo de `5/8` em agrupamento 2+3:

```json
{
  "numerator": 5,
  "denominator": 8,
  "beatUnit": "eighth",
  "grouping": [2, 3]
}
```

O modelo deve permitir que `grouping` seja explicitamente informado quando a fórmula possuir mais de uma interpretação musical válida.

---

## 8. Compassos simples

São compassos em que a organização convencional permite divisão binária de cada unidade principal.

Exemplos iniciais:

- 2/4
- 3/4
- 4/4
- 2/2
- 3/2
- 4/2

O sistema deve armazenar a fórmula completa, mesmo quando a interface oferecer atalhos para fórmulas comuns.

---

## 9. Compassos compostos

Nos compassos compostos, a unidade percebida de pulso normalmente corresponde a uma figura pontuada formada pela soma de três unidades menores.

Exemplos:

- 6/8 → 3 + 3
- 9/8 → 3 + 3 + 3
- 12/8 → 3 + 3 + 3 + 3

O Music Engine deve preservar essa estrutura para orientar:

- agrupamento de hastes;
- beaming;
- leitura visual;
- posicionamento de acentos;
- reprodução futura;
- edição e reinterpretação do ritmo.

---

## 10. Compassos assimétricos

Compassos como `5/8` e `7/8` precisam representar explicitamente seus agrupamentos.

Exemplo:

```text
5/8

2 + 3
♪ ♪ | ♪ ♪ ♪
```

ou:

```text
3 + 2
♪ ♪ ♪ | ♪ ♪
```

Para `7/8`:

```text
2 + 2 + 3
2 + 3 + 2
3 + 2 + 2
```

O sistema não deve substituir silenciosamente um agrupamento por outro.

Se o usuário escolher uma fórmula sem especificar agrupamento, o sistema poderá aplicar uma convenção padrão, mas essa decisão deve permanecer representada no modelo e ser alterável posteriormente.

---

## 11. Mudança de fórmula de compasso

Uma partitura pode mudar de fórmula ao longo do tempo.

Exemplo:

```text
4/4 | 4/4 | 3/4 | 6/8 | 4/4
```

A mudança deve ser armazenada como evento estrutural associado ao ponto temporal em que passa a valer.

Conceitualmente:

```text
Measure 1 → 4/4
Measure 2 → 4/4
Measure 3 → 3/4
Measure 4 → 6/8
Measure 5 → 4/4
```

A fórmula não deve ser uma propriedade fixa da partitura inteira.

---

## 12. Regra de compasso completo

O Music Engine deve calcular o preenchimento do compasso usando a duração temporal exata dos eventos.

Exemplo em `4/4`:

```text
4 × semínima = 1920 ticks
```

Se o compasso contém:

```text
semínima + semínima + semínima + semínima
```

então:

```text
480 + 480 + 480 + 480 = 1920
```

O compasso está completo.

---

## 13. Regra de excesso de capacidade

O sistema não deve permitir que um evento ultrapasse a capacidade do compasso sem uma decisão explícita do Music Engine.

Exemplo:

```text
4/4
capacidade = 1920

conteúdo atual = 1680
novo evento = 480
resultado = 2160
```

O evento excederia o compasso.

O comportamento esperado do núcleo é:

1. detectar o excesso;
2. preservar a intenção musical quando possível;
3. dividir o evento entre compassos quando a representação musical permitir;
4. aplicar ligadura entre as partes quando necessário;
5. nunca simplesmente truncar a duração sem informar o modelo.

A interface pode oferecer feedback visual, mas a decisão pertence ao Music Engine.

---

## 14. Avanço automático do cursor

A lógica de `Nota Pronta` depende da capacidade do compasso.

Exemplo:

```text
4/4

Inserir semínima
↓
posição = 480

Inserir semínima
↓
posição = 960

Inserir semínima
↓
posição = 1440

Inserir semínima
↓
posição = 1920

COMPASSO COMPLETO
↓
cursor avança para o próximo compasso
```

Essa regra deve operar sobre posições e durações do Music Model, e não sobre coordenadas gráficas.

---

## 15. Preenchimento e silêncio

Um compasso incompleto pode representar uma situação válida durante a edição, dependendo do estado do documento.

O editor pode permitir um estado temporário de composição, mas deve distinguir:

```text
compasso em edição
≠
compasso musicalmente finalizado
```

Ao finalizar, exportar ou reproduzir, o Music Engine poderá validar se os compassos possuem preenchimento adequado e, quando necessário, completar a estrutura com pausas implícitas ou explícitas conforme a regra do formato de saída.

A decisão de tornar pausas explícitas deve ser definida nas regras de representação/exportação, não escondida no renderer.

---

## 16. Agrupamento e renderização

O agrupamento rítmico é dado do domínio musical.

O renderer deve receber informação suficiente para desenhar corretamente:

```text
Music Model
    ↓
Music Engine
    ↓
estrutura rítmica validada
    ↓
Renderer
    ↓
partitura visual
```

O renderer não deve tentar descobrir sozinho se `7/8` significa `2+2+3`, `2+3+2` ou `3+2+2`.

---

## 17. Precisão temporal

Todas as operações temporais devem manter precisão exata.

Não usar cálculos aproximados em ponto flutuante para decidir se:

- um compasso está completo;
- um evento cabe no compasso;
- uma nota atravessa uma divisão temporal;
- duas durações são equivalentes;
- uma ligadura deve ser criada.

A implementação pode usar ticks, frações inteiras ou outro sistema exato, desde que a precisão musical seja preservada.

---

## 18. Futuras extensões

O modelo deve estar preparado para:

- fórmulas aditivas;
- mudanças frequentes de métrica;
- compassos alternados;
- polimetria;
- polirritmia;
- múltiplas vozes com estruturas rítmicas independentes;
- quiálteras;
- anacruses;
- compassos incompletos intencionais;
- notação proporcional ou contemporânea;
- importação/exportação via MusicXML;
- interpretação avançada para playback.

Esses recursos não fazem parte da primeira versão, mas o modelo inicial não deve impedir sua implementação futura.

---

## 19. Regras do Music Engine derivadas deste documento

```text
RHYTHM-001
Uma fórmula de compasso possui capacidade temporal calculável.

RHYTHM-002
Capacidade temporal não determina sozinha o agrupamento rítmico.

RHYTHM-003
O agrupamento rítmico deve ser representável explicitamente.

RHYTHM-004
Compassos compostos devem preservar sua organização perceptiva.

RHYTHM-005
Compassos assimétricos devem permitir diferentes agrupamentos válidos.

RHYTHM-006
Uma mudança de fórmula pode ocorrer em qualquer ponto estrutural apropriado da partitura.

RHYTHM-007
O Music Engine deve detectar excesso de capacidade antes de aceitar uma operação.

RHYTHM-008
O sistema não deve truncar silenciosamente uma duração musical.

RHYTHM-009
O avanço automático do cursor deve usar posição temporal, não coordenadas gráficas.

RHYTHM-010
O renderer não é responsável por determinar regras musicais de agrupamento.

RHYTHM-011
Operações temporais devem manter precisão exata.
```

---

## 20. Critérios de aceitação

O domínio será considerado consistente quando for possível representar, sem ambiguidade estrutural:

- `4/4` com agrupamento 4;
- `3/4` com agrupamento 3;
- `4/2` com capacidade correta;
- `6/8` como `3+3`;
- `9/8` como `3+3+3`;
- `12/8` como `3+3+3+3`;
- `5/8` como `2+3` ou `3+2`;
- `7/8` como `2+2+3`, `2+3+2` ou `3+2+2`;
- mudança de fórmula entre compassos;
- detecção de compasso cheio;
- detecção de overflow;
- avanço automático do cursor ao completar um compasso.
